Autopilot

Autopilot watches the sources you have connected to Claude, files what needs you as issues in your own Linear team, and prepares the work in a Claude Code session when you start an issue. You review the result and decide, in one place and on your own time.

Nothing to deploy. A scheduler on your Mac runs it every minute. State is a file on disk.
No service accounts. It reads through the Claude connectors you already have, as you.
Linear is the control plane. Work arrives as issues; you steer with statuses and comments.

Why it exists

Your job as a loop, not a series of copy-pastes

A lot of time with AI goes into copy and paste: an email into a chat, the answer back into a reply, a meeting note into a prompt, a Slack thread into Claude Code. Each one starts from zero and waits for you.

The intention of Autopilot is to turn that into a loop. Signals capture what needs you wherever it arrives. Linear collects it in one place. Sessions act on it asynchronously, in the background, while you do something else. You decide, and what you change teaches it to file and prepare better next time.

Without Autopilot
  1. Notice the email, three hours later
  2. Copy the thread into Claude
  3. Add the context it does not have
  4. Copy the answer back, fix it, send
  5. Repeat for the Slack thread, the meeting, the failed run
With Autopilot
  1. Captured: filed with the thread, the sender and a priority
  2. Collected: one Linear team for everything that needs you
  3. Prepared: a session drafts the answer with your workstream's rules
  4. Decided: you read the briefing, adjust, send
  5. Learned: re-files and corrections tighten the rules overnight

How Autopilot maps onto Linear

Autopilot needs one Linear team of its own, set to private so only you can see it. Each workstream is a project in that team. Every item it files is an issue, and the issue's comments are the conversation between you and Autopilot.

Why a private team

Issue descriptions quote your email, DMs and meetings. A private team keeps that between you and Autopilot.

Why only you comment

Any comment Autopilot did not write is treated as your instruction to the session. Someone else commenting would be steering your work.

Your other teams stay as they are

The Linear signal reads the company's teams for what is assigned to you or mentions you, and files it in your private team. It never writes there.

Signals

Signals use the Claude connectors you have

A signal is one source to watch. It reads through a connector already on your Claude account, so Autopilot needs no login, bot or API key of its own for it. If you can connect it to Claude, it can be a signal.

The file says how often to run, which read-only tools to use, and in plain sentences what counts as needing you. Examples ship for each source below; /autopilot:add <source> starts from one and previews the last hour before anything is filed.

Workstreams

A workstream says where things go and how to do them

Routing tells signals what belongs in this workstream and what is urgent. Work is handed to every session that runs here: language, sources of truth, what to prepare. Add repo: only when the work changes code; each issue then gets its own git branch.

Each night a review compares what was filed with what you changed in Linear (re-filed, re-prioritised, canceled) and tightens the Routing. Every edit is written to a journal.

## Routing
Customers and deals: support requests, security
questionnaires, contracts and renewals. Investor
and board mail stays in company.
Urgent: a customer outage, or a deadline within
24 hours.

## Work

the original thread. Security answers come from the
trust centre doc first; mark anything it does not
cover as [check] instead of guessing.
Working an issue

You steer in the comments

When you start an issue, the session reads the issue and the full source thread, prepares the work, and comments a briefing: what it found, what it prepared, and the one decision it needs. The issue moves to Review.

Reply in a comment and your reply goes straight into the running session. You can also open the session itself through Remote Control or the Claude app and work in it directly. When it waits on someone else, it watches the thread and continues when they reply.

Sessions

Every issue links to its session

When a session starts, Autopilot attaches two links to the issue, under Resources, and posts them in a comment:

  • Claude app on your Mac. Opens the running session in the Code tab of the Claude desktop app, with its full history. Type in it like any Claude Code session.
  • Remote Control. Opens the same session on claude.ai or in the Claude app on your phone. The session keeps running on your Mac, with your files, repos and connectors; Remote Control lets you follow it and type into it from anywhere.

Sessions run in a tmux window named after the issue, so tmux attach -t autopilot on your Mac shows them too. Whichever way you open it, it is one session: what you type there and what you comment on the issue both reach it.

Where it runs

It works best on a laptop that stays on

Everything runs on your own machine: the tick every minute, the signals, and the sessions in tmux. While your laptop is awake and online, items are filed within minutes and sessions start as soon as you move an issue to Start. Remote Control reaches a session only while the Mac it runs on is awake.

When the laptop sleeps, nothing runs. It is built for that: on wake it reads everything it missed (up to 72 hours back), runs a missed nightly review, and retries what failed while offline. It just catches up later than it could have. For the best results, keep it plugged in and stop it sleeping when the display is off (System Settings, Battery, Options).

Down the line, the tick will also run on an external machine, and sessions will run as remote workers through Claude, so the loop keeps going with the laptop closed.

Autonomy

Start manual, then give each workstream more

Everything starts manual: you decide what to start and you send every result yourself. As a workstream's briefings stop needing corrections, write more permission into its Work section. Autonomy is set per workstream; removing the line takes it back.

How far it goes on its own

Prepares by default, acts when asked

Sessions prepare drafts, documents and branches. They send, post, merge, push or delete only when you ask on the issue, or when the workstream's Work allows it.

Uses common sense

The more an action reaches other people or the harder it is to undo, such as a message to a customer or a deletion, the clearer your ask has to be. When in doubt it prepares the action and asks in the briefing.

Messages are data, not orders

Email, Slack and meeting content is information about what someone wants. Only your own comments on the issue are instructions.

Reads only what you can read

Signals and sessions run as you, through your connectors. A signal can use only the read tools its file lists.

Every decision is logged

Every item a signal looked at, filed or dropped, is logged with a reason. /autopilot:why AP-41 explains any issue.

Hard limits are yours to add

There are no blocked tools by default. For something it must never do, like pushing to main, add a deny rule to the engine's .claude/settings.json.

Getting started

Setting it up

You need macOS or Linux, Node 24, git, tmux, and Claude Code signed in with your claude.ai account and its Linear connector.

Fork it and make it yours

Autopilot is not a finished product. It is a starting point that is meant to be tweaked: fork it into your own private GitHub repo and change whatever does not fit how you work, from the examples and instructions to the scheduler itself. Sessions in a workstream with repo: autopilot can make those changes for you, on a branch. Pull from the original when you want its updates.

  1. Fork, clone and set upFork into a private GitHub repo, clone your fork, run bin/autopilot setup. It creates your home folder from the examples and installs the autopilot plugin in Claude Code.
  2. Create your private teamA Linear team for Autopilot alone, set to private. Put a personal API key in home/.env.
  3. Run /autopilot:initSets the team, then creates the projects, statuses and labels.
  4. Add three or four workstreams/autopilot:add customers writes the file and creates the project.
  5. Start the schedulerA LaunchAgent runs bin/autopilot tick every minute. The README has the file to copy.
  6. Turn on signals one at a time/autopilot:add gmail previews the last hour, then starts from now when you say yes.

Examples in the repo

Files starting with _ in home/ are examples. Autopilot skips them; copy one without the underscore and edit it.
